# Accounts and keys

Every agent account is a smart-contract wallet that its principal owns. Agent Bank never holds a key that can move funds by itself: it holds a co-signing key that can only add a second signature, or refuse to.

## The hierarchy

1. **Organization** (the principal): KYC/KYB-verified; owns agents; holds policies, members (admin, approver, viewer) and API keys. Its `owner_address` is the principal's owner key.
2. **Agent**: a named software identity with optional ERC-8004 id and agent card URL; its `did` is a `did:pkh` of its primary account. Status `active` or `frozen`.
3. **Account**: one smart account per agent per chain (`role: "agent"`), plus one **treasury** account per org (`role: "treasury"`, no agent). The address is counterfactual (CREATE2), so it can receive funds before it is deployed. An agent account deploys with its **setup operation**, the owner-signed install of its first session.
4. **Pockets**: ledger-only sub-balances of an account (`operating`, `reserved`, `escrow`, `stream`, `fees`, `savings`, vaults). They never need their own address. See [The ledger](/concepts/ledger).

## The smart account

Each account is a **Safe** (v1.4.1) with the **Safe7579** adapter, so it accepts ERC-7579 modules, deployed through the Safe7579 launchpad and operated through ERC-4337 (EntryPoint v0.7) with a bundler and paymaster. The modules that matter:

| Module                           | Role                                                                                                                                     |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Smart Sessions (Rhinestone)      | Holds each session key's on-chain scope; its session validator is an `OwnableValidator` configured **2-of-2: session key and co-signer** |
| `AgentPolicyHook`                | Agent Bank's hook: per-call value cap and daily cap in UTC-day buckets, checked on every session operation                               |
| `TopUpExecutor`, `SweepExecutor` | Owner-installed executors for auto top-up and the treasury sweep (see [Savings and treasury](/concepts/savings))                         |

**Gas.** An Agent Bank paymaster sponsors gas; the cost accrues in USDC to the account's `fees` pocket and is swept with a later operation, so agents never hold ETH.

## The keys

| Key           | Held by                                 | Can do alone                                                                                      | Typical form                               |
| ------------- | --------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------ |
| **Owner**     | The principal                           | Everything: withdraw all funds, remove the co-signer, rotate keys, install sessions and executors | Passkey, hardware wallet (Ledger, YubiKey) |
| **Co-signer** | Agent Bank, in a separate cloud account | Nothing. Approves or refuses agent-initiated operations                                           | AWS KMS secp256k1 key, never exportable    |
| **Session**   | The agent runtime                       | Nothing. Signs requests and operations inside its scope, which the co-signer must also sign       | secp256k1 key generated by the SDK, 24 h   |
| **Spend**     | The agent runtime                       | Spend its own small USDC float, for x402 only                                                     | secp256k1 EOA generated by the SDK         |

### The validation rule

On-chain, an operation is valid if **the owner signs it**, or if **a live session key and the co-signer both sign it** and the session's policies and the `AgentPolicyHook` pass:

```text
valid = owner ∨ (session ∧ co-signer ∧ policy)
```

So a stolen session key is useless without the co-signer; a compromised co-signer key is useless without a session key; and both together are still bounded by the session's on-chain scope. The owner can act alone at any time, including through the Safe's native `execTransaction`, which bypasses the ERC-7579 modules and hooks entirely; that is what the [exit tool](/concepts/exit-tool) uses.

## Session keys

A session key is generated client-side (by the SDK, from the platform's CSPRNG) on the agent's machine; only its address is registered. It signs two things: every API request, as an [RFC 9421 signature](/guides/request-signing), and the `user_op_hash` of each payment, escrow or stream operation, as an EIP-191 personal message over the raw 32 bytes.

### Scope

The owner grants a session with a scope that is installed on-chain:

| Field                | Meaning                                                                                                           |
| -------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `asset`              | `USDC`                                                                                                            |
| `max_per_tx`         | Largest single operation, decimal USDC                                                                            |
| `max_per_day`        | Daily total, decimal USDC (the on-chain hook counts UTC days; see [Policies](/concepts/policies#rolling-windows)) |
| `allowed_recipients` | Optional: at most 100 addresses the session may pay                                                               |
| `allowed_contracts`  | Optional: at most 20 contracts (escrow, streams) the session may call                                             |
| `expires_at`         | Expiry: 24 hours by default, at most 7 days                                                                       |

The co-signer stores the same scope, verified against the owner's `session.grant` authorization, and checks it too (`session.max_per_tx`, `session.max_per_day`, `session.allowed_recipients`, `session.allowed_contracts`, `session.expired`, `session.revoked`). When an agent acts under a [mandate](/concepts/mandates), its scope is the intersection of the policy's and the mandate's caps.

### Lifecycle

`pending_install` → `active` → `expired` or `revoked`.

1. The owner signs a `session.grant` [owner authorization](/concepts/owner-operations#owner-authorizations) over `{ account_id, public_key, scope }`; `POST /v1/sessions` registers it.
2. `POST /v1/sessions/{id}/install` prepares the Smart Sessions install as an [owner operation](/concepts/owner-operations); the owner signs it.
3. To revoke, `DELETE /v1/sessions/{id}`: the co-signer refuses the key immediately. The owner should also revoke it on-chain (owner operation `session.revoke`), the hard backstop.

Sessions are short-lived by design: rotate by granting a new one before the old one expires.

## The spend key

x402's `exact` scheme pays with an EIP-3009 `transferWithAuthorization` signature on USDC. A deployed Safe could sign one through ERC-1271, but the transfer then runs inside the USDC contract, outside the account's hooks and session policies, so the on-chain caps would not apply; an undeployed account cannot sign at all. So each agent has a **spend key**: a plain EOA that holds a small USDC float and signs x402 authorizations only, and agent sessions never get ERC-1271 signing rights ([ADR 0001](/operations/adrs)). Agent Bank still decides every x402 payment: the agent must call `POST /v1/x402/pay`, the co-signer checks the policy, and the API returns the exact authorization to sign, with a nonce derived from the payment id that the indexer matches on-chain.

- The float is refilled from the smart account by a normal payment to the spend key (kind `refill`, no fee), which the session key and co-signer sign under policy (`refill.target`), so the on-chain caps bound cumulative x402 spend at the refill.
- Keep the float small: about one day of expected x402 spend, at most 25 USDC during the beta. The loss bound of a fully compromised agent is the float. A spend-key payment that bypasses `/v1/x402/pay` shows up in reconciliation as an unmatched outflow and pauses the agent's sessions.
- The spend key is generated client-side by the SDK, next to the session key, and Agent Bank never holds it. It must be a fresh key that no other account uses, and once attached it cannot be replaced: the co-signer pins it.

### Float-recovery permit

The float sits outside the smart account, where the owner's own exit path cannot reach it. So at provisioning the spend key signs an EIP-2612 `permit` on USDC: owner = the spend key, spender = the agent's smart account, with the maximum value and deadline by default. The account's setup operation executes it; from then on the account, or the owner's [exit tool](/concepts/exit-tool) (`sweep-spend-keys`), can pull the float home with `transferFrom`, without the agent.

The permit names the account's address, so the order is fixed: create the account, sign the permit for `account.address`, attach both with `PUT /v1/accounts/{id}/spend-key`, then install the first session. The permit can only run in that setup operation (afterwards the `AgentPolicyHook` refuses token calls other than transfers and approvals), so attaching one to an account that is already set up fails with `invalid_state`.

`account.spend_key_permit` tracks it: `none` (no permit attached), `pending` (waiting for the setup operation) and `executed`. If the setup operation fails, the permit is dropped back to `none`: attach a new one.

```ts
import { generateSessionKey, generateSpendKey } from "@agentbank/sdk";

const spendKey = generateSpendKey();
const sessionKey = generateSessionKey();
// Create the account, sign and attach the permit, then grant and install the first session.
const { account, session } = await principal.setupAgentAccount({
  agentId: agent.id,
  spendKey: spendKey.account,
  session: {
    publicKey: sessionKey.address,
    scope: { max_per_tx: "25.00", max_per_day: "200.00" },
    waitForInstall: true,
  },
});
console.log(account.spend_key_permit); // "executed"
```

For an account that already exists but is not set up yet, `principal.provisionSpendKey(account.id, spendKey.account)` signs and attaches the permit; `signSpendKeyPermit` signs one by hand. A key that has signed permits before needs its current USDC `nonces(spendKey)` as `nonce` (exported as `EIP2612_NONCES_ABI`).

## Authentication to the API

| Caller                 | Mechanism                                                                                                             |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Agent                  | [RFC 9421 request signature](/guides/request-signing) by the session key; at most 300 seconds valid; single-use nonce |
| Principal (automation) | `Authorization: Bearer abk_test_…` org API key; only its SHA-256 is stored                                            |
| Principal (console)    | Passkey (WebAuthn) sign-in; approvers decide with a passkey                                                           |
| Owner actions          | EIP-712 `OwnerAuthorization` signature in the request body, valid at most 15 minutes                                  |

## Freezing

Freezing is a tightening, so it is immediate: `POST /v1/agents/{id}/freeze` (one agent) or `POST /v1/orgs/me/freeze` (every agent). The co-signer then refuses everything for that agent or org (`agent_frozen`, `org_frozen`). Unfreezing is a loosening: it needs an owner authorization (`agent.unfreeze`, `org.unfreeze`) and takes effect after one hour.

## Recovery

A lost owner key is recovered **on-chain** by guardians the principal chooses, with Candide's audited `SocialRecoveryModule` in its 72-hour variant ([ADR 0013](/operations/adrs)):

- Guardians confirm a new owner; once enough have confirmed, a **72-hour time lock** starts. The current owner can cancel at any point during it, and every recovery alerts the principal on all channels.
- After the delay anyone may finalize; the Safe's owner becomes the new key. A guardian can never become an owner.
- **Agent Bank may hold one guardian seat but never a majority.** The provisioning flow requires a strict majority threshold, and a threshold of at least 2 whenever Agent Bank holds a seat; the default is three guardians (two of the principal's and one Agent Bank key, separate from the co-signer) with a threshold of 2. The module does not enforce this itself, so the indexer alerts on any guardian change that breaks it.
- Only the owner configures recovery, and agent sessions can never call the recovery module.

Recovery replaces the Safe owner only: the new owner should revoke the existing session keys and review the modules, and Agent Bank operators rotate the owner key off-chain after verifying the recovery ([owner recovery runbook](/operations/runbooks#owner-recovery)).

A **voluntary** rotation, while you still hold the old key, needs no guardians: sign an `owner.swap` operation per account and an `owner.rotate` authorization with the current key ([Rotating the owner key](/concepts/owner-operations#rotating-the-owner-key)).
